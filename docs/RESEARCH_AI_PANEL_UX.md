# 调研：AI 写作面板 UX 优化

> 日期：2026-06-01
> 范围：竞品 AI 写作面板交互模式分析 + 当前 AIPanel 问题诊断 + 重设计方案

---

## 一、当前 AIPanel 结构诊断

当前面板共 6 个 section，平铺展开：

| # | 区块 | 内容 | 问题 |
|---|---|---|---|
| 1 | 写作操作 | 4 个等权重大按钮（起草/润色/检查/状态） | 四个操作的**使用频率和时机完全不同**，却放在一起 |
| 2 | 局部改写 | 选区信息 + 7 个操作按钮 + 自然语言输入 | 7 个按钮中"缩写""润色""扩写"使用频率远高于"去AI味""对白"，但权重一样 |
| 3 | 章节提示 | 当前章大纲摘要 | 纯信息展示，不参与交互 |
| 4 | 章节节奏 | BeatSheet 组件 | **起草前**才有用的工具，却一直显示 |
| 5 | 活跃角色 | bible 角色卡片 | 参考信息，应该是折叠的 |
| 6 | 一致性检查结果 | 按需显示 | 合理 |

**核心问题**：所有功能都是**平等的、静态的**排列。用户打开面板后面对的是一个"功能超市"——不知道该先拿哪个。实际上，写作是一个**有顺序的过程**：

```
空章节 → 生成初稿 → 审校修订 → 最终确认
         ↓
      (可选)先生成节拍再起草
         ↓
      (随时)选中文字→定向改写
```

但 AIPanel 没有把这个流程表达出来。

## 二、竞品模式分析

### 2.1 Sudowrite（市场标杆）

**交互模式**：分阶段引导（Story Engine）

```
Brainstorm → Outline → Beats → Prose → Revise
   ↓           ↓         ↓        ↓        ↓
  灵感发散    大纲规划   章节节拍  正文起草  逐段精修
```

每个阶段是独立的一屏，用户完成一个再进入下一个。不是把所有功能摊开，而是**一步一步引导**。

**关键手法**：
- 当前在哪个阶段，视觉上非常明确（进度条 + 标题）
- 只显示当前阶段需要的操作
- 提供"跳过"和"返回"的灵活性

### 2.2 Notion AI

**交互模式**：选中触发 + 上下文菜单

```
选中文字 → 浮动菜单弹出 → 选择操作（或输入自然语言指令）
```

**关键手法**：
- 无选中 = 无操作入口（减少认知负荷）
- 自然语言指令作为核心交互，预设操作作为快捷方式
- 结果直接嵌入文档，可继续编辑

### 2.3 Cursor（AI 代码编辑器）

**交互模式**：`Cmd+K` 指令栏 + 选中触发

```
选中代码 → Cmd+K → 输入自然语言 → diff 预览 → 接受/拒绝
```

**关键手法**：
- 核心交互只有**一个入口**（`Cmd+K`）
- 所有 AI 操作通过自然语言表达，不需要记忆按钮
- 变化在 diff 视图中呈现，所见即所得

### 2.4 NovelAI

**交互模式**：极简"继续写"

```
写一段 → AI 续写 → 接受/重试 → 继续
```

**关键手法**：
- 只有一个主要操作：让 AI 继续写
- 所有复杂度藏在配置项里（默认隐藏）
- 即时反馈，不打断心流

## 三、最佳实践的共性

| 原则 | 说明 |
|---|---|
| **分阶段** | 不把起草、修订、检查放在同一屏，按写作的自然节奏组织 |
| **上下文驱动** | 空章节时显示起草入口，有内容时显示改写入口 |
| **主次分明** | 每个阶段只有一个"主要操作"，其余折叠为辅助工具 |
| **自然语言优先** | 预设按钮是快捷方式，自然语言指令是真正的灵活通道 |
| **即时反馈** | 每次 AI 操作结果直接可见（候选稿 / diff / 预览），不跳出上下文 |

## 四、重设计方案

### 4.1 核心思路：**按写作阶段自适应**

AIPanel 根据当前章节状态，显示**不同模式**：

#### 模式 A：空章节（无正文内容）

```
┌──────────────────────────────────┐
│  灵感助手                         │
├──────────────────────────────────┤
│                                  │
│  本章尚为空。                     │
│                                  │
│  ┌────────────────────────────┐  │
│  │  ✨  生成初稿               │  │
│  │  基于大纲和角色设定自动起草  │  │
│  └────────────────────────────┘  │
│                                  │
│  ── 或者先规划节奏 ──            │
│  生成节拍 → 编辑节拍 → 再起草    │
│                                  │
│  ── 参考 ──                      │
│  📋 本章大纲摘要（折叠）          │
│  👤 活跃角色（折叠）              │
└──────────────────────────────────┘
```

#### 模式 B：有正文内容

```
┌──────────────────────────────────┐
│  灵感助手                         │
├──────────────────────────────────┤
│                                  │
│  💬 告诉 AI 你想怎么改            │
│  ┌────────────────────────────┐  │
│  │  描述你的修改需求…      →  │  │
│  └────────────────────────────┘  │
│  ↑ 选中一段文字后更有针对性       │
│                                  │
│  未选中文字？对整个章节操作：     │
│  [润色] [扩写] [缩写] [对白]     │
│                                  │
│  ── 工具 ──                      │
│  一致性检查  ·  状态分析  ·  重新起草  │
│                                  │
│  📋 活跃角色（折叠）              │
└──────────────────────────────────┘
```

#### 模式 C：有候选稿正在审阅

保持现有 CandidatePanel 流程不变。

### 4.2 关键变化

| 现在 | 改为 |
|---|---|
| 4 个等权重大按钮 | 模式 A：1 个大 CTA（生成初稿），其余折叠；模式 B：输入框为主 |
| 7 个改写按钮平铺 | 保留 4 个高频操作作为 chips，其余收起 |
| BeatSheet 一直显示 | 只在空章节时作为"可选前置步骤"出现 |
| 角色卡片始终展开 | 默认折叠，点击展开 |
| 大纲摘要占空间 | 合并到章节提示里，模式 A 显示 |

### 4.3 自适应状态判断

```typescript
const panelMode = useMemo(() => {
  if (candidateOpen) return 'review';      // 模式 C
  if (!content.trim()) return 'empty';      // 模式 A
  return 'editing';                         // 模式 B
}, [candidateOpen, content]);
```

## 五、实施建议

这次改动**不改任何 API 或底层逻辑**，只改 AIPanel.tsx 的渲染层。

1. 按三种模式拆渲染分支
2. 模式 A 突出"生成初稿"CTA，BeatSheet 折叠到"先规划节奏"下
3. 模式 B 把 InstructionInput 提到最显眼位置，按钮降级为辅助 chips
4. 角色卡片和章节摘要默认折叠
5. 一致性检查和状态分析收到底部工具栏

文件改动面：仅 `AIPanel.tsx` 一个文件（约 100 行结构调整），零后端改动。
