# 调研：CLI 之外的方向探索

> 日期：2026-06-01
> 范围：竞品分析 + 市场定位 + 已有资产盘点 + 方向建议
> 优先级：低（探索性调研，非开工任务）

---

## 一、竞品全景图

### 1.1 海外 AI 小说工具

| 产品 | 定位 | 核心能力 | 月费 | 短板 |
|---|---|---|---|---|
| **Sudowrite** | AI 小说协写（市场第一） | Story Engine 引导式逐章写作、brainstorm、beat 生成、rewrite/expand、Canvas 可视化规划 | $19-44 | 英文 only、无自动全本生成、无质量门 |
| **NovelAI** | AI 故事+图像生成 | 文本冒险模式、图片生成、社区模组 | $10-25 | 偏二次元/轻小说、长程一致性弱 |
| **ChatGPT/Claude** | 通用 AI 对话 | 自由对话写作 | $0-20 | 无项目管理、无长程记忆、需人工组织上下文 |
| **Scrivener** | 传统写作工具 | 顶级项目管理、corkboard、分卷组织 | 买断 $59 | 无 AI、桌面端为主 |

Sudowrite 是最接近的参照物。它的 Story Engine 是"半自动引导式"——用户每章做选择，AI 生成候选，用户确认或修改后继续。这是目前验证过的产品形态，月活作者数万。

### 1.2 国内 AI 写作工具

| 产品 | 定位 | 现状 |
|---|---|---|
| **阅文/起点内部工具** | 平台内部 AI 辅助 | 未公开，仅内部作者可用 |
| **番茄小说** | 免费阅读平台 | 传闻有 AI 辅助创作工具，未对外 |
| **各类 AI 写作助手** | ChatGPT 套壳 | 大多是无结构的自由对话，无长程能力 |
| **彩云小梦** | AI 续写 | 偏娱乐向，续写质量不稳定，无项目结构 |

**核心发现：国内没有一款专门面向长篇小说创作的 AI 工具。** 这是一个空白市场。

### 1.3 中文网文作者的独特需求

- **日更压力**：4000-6000 字/天是生存线，AI 辅助的刚需极强
- **章均 2000-3000 字**：比英文小说更短，更碎片化
- **类型化严重**：玄幻/都市/言情/历史各有固定套路，"不踩线但又有新意"是核心
- **成本敏感**：大量兼职/业余作者，月预算有限
- **移动优先**：很多作者用手机码字

## 二、本项目已有资产盘点

| 资产 | 成熟度 | 竞品对比 |
|---|---|---|
| 全自动逐章生成（无人值守 40 章跑通） | ✅ 已验证 | **Sudowrite 无此能力**（它是逐章引导，不是无人值守） |
| 7 维质量门（plot_progress / continuity / logic / ai_voice / world_rules / character_consistency / prose_readability） | ✅ 已验证 | 竞品均无自动质量评分 |
| RAG 长程记忆（pgvector + HNSW + 混合检索） | ✅ 已验证 | NovelAI 无、Sudowrite 有基础版 |
| State-diff 故事状态追踪 | ✅ 已验证 | 竞品均无显式状态管理 |
| 候选稿机制（AI 生成不直接覆盖正文） | ✅ 已落地 | Sudowrite 有类似交互 |
| 章节版本恢复 + diff 对比 | ✅ 已落地 | Sudowrite 有、NovelAI 无 |
| 中文写作全链路 | ✅ 已落地 | **独特优势**——竞品均为英文优先 |
| 成本追踪与上限控制 | ✅ 已落地 | 竞品通常不透明 |

**结论**：底层引擎在中文长篇小说领域已经是第一梯队，但外层产品形态和交互还有巨大空间。

## 三、值得探索的 6 个方向

### 方向 1：交互式写作模式（建议优先级最高）

**现状**：Web 编辑器有 AI 面板，但交互是"点按钮 → 等生成 → 接受/拒绝"。CLI 有指令面板（`/rewrite` `/note` 等），但仍是结构化指令。

**要做的事**：把 AI 协写变成**对话式**的。用户选中一段文字，输入自然语言指令：

```
"这段打戏节奏太慢了，加一些沈言剑魂觉醒的视觉描写，控制在 300 字内"
"把林玥的对白改得更冷一点，她现在是卧底身份不应该这么热情"
"在第 15 章和第 18 章之间加一段过渡，解释为什么蒋阶突然改变了态度"
```

技术上需要：
- 选中文本上下文注入（已有 `editorSelection` 机制）
- 指向性修改 prompt（只改指定段落，不动其他——目前的 `onReviseSelection` 已有雏形）
- 修改意图理解（轻量 LLM 调用做意图分类：扩写/缩写/改风格/加描写/改对白/修逻辑）

**为什么优先级高**：全自动适合"生成初稿"，但真正写作的核心场景是"改稿"。这是从"生成器"升级为"写作伙伴"的关键一步。Sudowrite 正是靠这个交互模型建立了用户粘性。

**复用的现有代码**：`useChapterEditor`（选中区域）、`onReviseSelection`（局部修订）、`CandidatePanel`（候选稿对比）、`AIPanel`（交互容器）

---

### 方向 2：长程一致性工具面板

**现状**：7 维质量门在自动生成时运行，但结果只在 `needs_review` 时暴露。正常跑完的 40 章，质量数据被封存在 DB 里，作者看不到。

**要做的事**：做一个**独立的"小说体检"面板**，在任何时候都可以跑，输出结构化报告：

```
📊 《逆魂纪》一致性体检

伏笔追踪
  ✅ 第 3 章「蒋阶袖口暗红纹路」→ 第 28 章回收（剑魂封印标记）
  ⚠ 第 8 章「后山禁地的第三道门」→ 未回收（40 章内未再提及）
  ⚠ 第 12 章「天代宗使者的玉佩」→ 未回收

人物弧光
  沈言：对话风格从"犹豫"渐变到"决断"（ch1-10 迟疑词 12/章 → ch31-40 迟疑词 3/章）✅
  林玥：出场频率 ch15-25 骤降（8 章未出场），疑似被遗忘 ⚠

时间线
  故事内时间：约 3 年 2 个月
  ⚠ 第 22 章提到"立秋"，第 23 章紧接着说"春分已过"——时间跳跃未说明

章节节奏
  字数分布：ch1-5 平均 3200 字 → ch20-25 平均 4800 字（趋势偏长）
  最短章：ch7「暗室听审」2100 字
  最长章：ch24「天代宗试炼」5400 字
```

技术可行性：大部分检查是**零 token 启发式**（正则匹配伏笔关键词、字数统计、对话风格聚类）。少部分需要轻量 LLM 调用（如判断两个描写是否指向同一个伏笔）。

**为什么有价值**：这是目前所有竞品都**没有**的能力。40 章以上长篇的一致性管理是真实痛点，而项目已有的 7 维评分、state-diff、RAG 检索都是做这块的完美基础设施。

**复用的现有代码**：`evaluateNovelQuality`（7 维评分）、`retrieveMemories`（RAG 检索）、`applyStateDiff`（状态追踪）、`novelQualityBaseline`（基准数据）

### 方向 3：章节分支/多版本写作

**现状**：有版本历史（autosave/manual/ai），但是一维时间线。不能同时保留两个不同的创作方向。

**要做的事**：允许用户对同一章创建**命名分支**：

```
第 15 章「长老窥探」
├── main（当前主线）
├── 尝试：沈言直接揭露身份      ← 分支 1
└── 尝试：沈言继续隐瞒但留线索   ← 分支 2
```

分支可以独立续写（各自的第 16 章），最后用户选择一个分支合并回主线。这本质上是写作界的"git branch"。

**为什么有价值**：创作者经常纠结"这个情节走向好还是那个好"。目前的做法是手动复制粘贴不同版本，很容易乱。分支机制让探索性写作变得安全——随时可以回来。

**复用的现有代码**：版本历史系统（`ChapterVersion` 表）、`DiffView`（差异对比）、`VersionsModal`（版本管理 UI）

---

### 方向 4：中文网文专用工作流

**现状**：通用写作工具，没有针对网文品类的定制。

**要做的事**：
- **日更追踪器**：设定日更目标（如 4000 字），自动统计今日产出，显示连续更新天数
- **类型模板**：玄幻/都市/言情/历史/科幻各有固定的大纲骨架（如玄幻的"废柴→奇遇→宗门→试炼→天劫→飞升"），作为起点加速开书
- **爽点密度检查**：网文讲究"三章一小爽、十章一大爽"，统计打脸/突破/反转事件分布
- **水文检测**：标记明显水字数的段落（大量环境描写、重复对话、无推进的日常）
- **平台格式导出**：导出为起点/番茄等平台的投稿格式（含简介模板、标签建议）

**为什么有价值**：这是切中国市场的差异化打法。海外工具不会做这个，国内大厂的内部工具不对外开放。这个方向的很多功能是**零 token 纯规则**的（如爽点检测可以关键字匹配，水文检测可以统计信息密度）。

---

### 方向 5：成本优化智能推荐

**现状**：有成本追踪和上限控制，但用户需要自己判断用什么模型、什么参数。

**要做的事**：
- **分阶段模型建议**：大纲规划用便宜模型（如 deepseek-chat），正文起草用质量模型，审校用便宜模型
- **预估引擎**：在启动生成前给出"预计 ¥X.XX（基于历史同类型小说的实际成本）"
- **成本/质量分析**：对比不同模型在同一章上的质量和成本，给出性价比建议
- **省钱模式**：一键切换到"预算优先"配置（如跳过审校、降低自修轮数）

**为什么有价值**：网文作者成本敏感。实测 40 章跑完 1.51 元已经很便宜，但如果作者月产 2-3 本，对成本会更在意。这个方向不复杂——本质就是一个推荐引擎 + 历史数据统计。

**复用的现有代码**：`usage.ts`（成本追踪）、`llmUsage` 表（历史调用记录）、`generationPolicy.ts`（策略配置）

---

### 方向 6：Web 版终端式面板（把 CLI 体验搬进浏览器）

**现状**：CLI 是独立终端应用，Web 是传统网页。两个产品、两套代码。

**要做的事**：在 Web 编辑器里嵌入一个**终端风格的实时面板**（类似 CLI 设计的 Ink 面板），用于：
- 自动生成时的实时进度（替代当前简陋的轮询进度条）
- 查看逐章质量轨迹（折线图？纯文本？）
- 实时成本滚动（每章花费滚动刷新）
- `Ctrl+K` 指令面板（和 CLI 共享同一套指令系统）

可以通过 xterm.js + 自定义前端组件实现，不需要真正的 PTY，只需要模拟终端渲染风格。

**为什么有价值**：把 CLI 和 Web 打通。用户在 Web 上启动自动生成后，可以打开"终端视图"获得和 CLI 一样的沉浸式体验。CLI 的指令系统（`/rewrite` `/note` `/ending` 等）在 Web 上同样可用——只是渲染层从 Ink 换成 Web 组件。

**复用的现有代码**：CLI 的指令解析逻辑（抽象为纯函数）、`AutoGeneratePanel`（Web 端生成控制）

## 五、一句话总结

这个项目的底层引擎（全自动生成 + 质量门 + 长程 RAG + 状态追踪）在**中文长篇小说**这个细分领域已经是无人区。CLI 做好后，最值得做的是**把引擎的独特能力暴露给写作者**——不是堆更多 AI 能力，而是把已有的 7 维评分、伏笔追踪、状态演变变成写作者能看懂、用得上的产品界面。

交互式写作（方向 1）和一致性工具（方向 2）是两个最自然的下一步，都建立在已有代码之上，且填补了竞品从未触及的空白。
